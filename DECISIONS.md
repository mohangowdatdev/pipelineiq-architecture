| 19 | Apr 2026 | Catalogue entity ID generation | UUID5 (deterministic, hash-based) | UUID4 is random — re-seeding the catalogue after a table drop produces different IDs and breaks all FK references in order_lines and inventory_snapshot. | 20 | Apr 2026 | Inventory snapshot transaction scope | Separate transaction from main data batch | The snapshot is 189,000 rows (4,200 products × 45 stores). Including it in the main transaction increases lock hold time and timeout risk on Azure SQL serverless. It's also idempotent by snapshot_date — failure is safe to retry. Main batch (customers + orders + status + dimension changes) must be atomic together; snapshot does not need to be. |
| 21 | Apr 2026 | Dependency violation failure scenario | Control flag in velora_oms.control_flags table | The dependency_violation scenario needs a mechanism for ADF to read a signal that triggers out-of-order execution. | 22 | Apr 2026 | Generator module separation | One module per domain (customers, orders, status, dimensions) | Each module owns one domain of write operations. Customers.py generates INSERTs and UPDATEs for CRM tables only. Orders.py writes to OMS only. This separation means a bug in one module cannot corrupt another domain's data. It also makes each module independently testable without running the full generator. |
| 23 | Apr 2026 | Failure injector scope | Mutates in-memory batch before DB write, not after | The injector operates on pandas DataFrames before any SQL transaction opens. This means: (1) the failure is guaranteed to be written or not written as a unit, (2) no partial-injection state can exist in the DB, (3) the injector is independently testable without a DB connection. |

| 40 | Apr 2026 | `pyodbc.Cursor.fast_executemany = True` is load-bearing for all `executemany` in the generator (and any future pyodbc-based code) | Every cursor created against Azure SQL must set `cursor.fast_executemany = True` before any `executemany` call. Applied at 3 sites: `generator/catalogue.py::_bulk_insert`, `generator/main.py::run` (main transaction cursor), `generator/main.py::_write_inventory` (inventory snapshot cursor). | Without this flag, pyodbc sends each row as a separate SQL statement (one TDS packet per row). Over laptop → centralindia network (~200ms RTT), 4,200 product inserts exceed the 30s connection timeout and hit `[08S01] TCP Provider: Error code 0x274C (10060)` / `Communication link failure`. With the flag, pyodbc binds parameters on the client side and sends one batched TDS request — 189K inventory rows went from unrecoverable timeout to ~5 minutes. Also note: `fast_executemany` is a **cursor-level** attribute (not connection-level), so it must be set on each new cursor. Any future pyodbc code against Azure SQL in this project must set it. |
